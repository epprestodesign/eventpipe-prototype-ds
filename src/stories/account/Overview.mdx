## Phase 1 specification

Keep the recognizable split composition: EventPipe branding at left, credentials or reset request at right. Use the existing logo, design tokens, field wrapper, inputs, buttons, links and typography. The two screenshot-based baselines are **Today’s login** and **Today’s reset**, at the end of Log in and Forgot password.

The improved login asks for email and password, with Log in and Forgot your password. The reset request asks for email, with Cancel and Reset Password. Cancel returns to login and keeps the entered email. The password is cleared on navigation. The proposed refinements add clearer reset copy, accessible show/hide password, validation messages and focus movement when changing screens.

**Proposed supporting states, not explicit Rob requirements:** invalid or missing input, incorrect credentials, submitting, service unavailable, session expired, reset submission failure and reset-request confirmation. The confirmation uses the same wording whether an account exists or not. These are reviewable UI states, not a backend authentication implementation.

## Phase 2 specification

Three method stories under **Right panel › MFA methods**, plus **Full flow** at the top of the section, keep the sidebar compact. Each has a **Preview state** selector and **Restart preview** button above the product screen; these are review controls only.

| Milestone | States available inside the story |
| --- | --- |
| Email code | Enter code/countdown, incorrect code, expired code, resend available, code resent, resend failed, verifying, session expired |
| Authenticator | Enter code, incorrect code, expired code, verifying, session expired |
| Choose another method | Both methods, email only, authenticator only, no available method |
| Full flow | Start at login, email, or authenticator; after log in it leads with the email code, then continues through verification to completion |

Changing the selected state resets entered data and timers. Edge cases are reviewed using these selectors rather than as separate stories.

After credentials are accepted and the server requires MFA, show the account’s eligible challenge. Authenticator users can choose **Try another way**, then email where available. Email users can resend a code or choose another eligible method. Returning to login clears the challenge form.

**Proposed supporting states:** invalid code, expired email code, verifying, resend success/failure, verification-session expiry, one available method and no available method. In the last state the preview directs users to their account administrator; the actual recovery/support destination needs confirmation.

The code entry and resend line use Account’s copy of the six-box interaction first built for Account V2, including paste, numeric input, autofill and error styling. The email resend countdown starts at an illustrative 0:42 and ticks down; expired email codes require a resend, while expired authenticator codes can be replaced with the latest app code. This preview timing is not a backend policy decision. The masked sample email and preview success behavior are illustrative. The prototype accepts any six digits, never contacts an authentication service and never sends email. The loading stories remain loading so they can be reviewed. The interactive story connects credentials → email code → completion, with **Try another way** → authenticator one step away.

## Product-update surface

Use an optional card made from existing GUI components, plain title/body text and an optional destination link. Empty content leaves the brand-only panel. Long content wraps; on small screens the announcement follows the form. Copy shown in these stories is a sample, not an announcement that a feature shipped.

Rob supported this direction, but did not commit it to the first migration release. A CMS, rich-text editor, permissions, publishing workflow, scheduling and analytics were not specified and are not built here. Stored content is rendered as text rather than raw HTML.

## Left rail

**Left rail** holds every brand-panel treatment. Each can be reviewed beside any right-panel screen (**Right panel** toggle: Sign up, Log in, Email code, Authenticator) or on its own with **Component only**. **Read more link** turns the optional action on/off; **Image unavailable** checks the image treatment’s fallback.

| Treatment | Intended use |
| --- | --- |
| Brand only | The logo alone — the default when there is no product news |
| Value props | The original Account headline and three value points, for prospects as much as customers |
| What’s new card | The simplest editable surface: a title, body and optional link in a card |
| Featured Article | One editorial headline directly on the navy panel; minimal visual clutter |
| Release Highlights | A compact digest of several improvements from one product roundup |
| Rotating Spotlight | Three articles with manual previous/next controls; no automatic motion during MFA |
| Product Tip | One practical workflow reminder in the existing banner component |
| Image Announcement | Blog artwork and a short announcement in the existing card surface |
