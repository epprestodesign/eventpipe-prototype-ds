## 01 · Email Settings — the new row

**Asked for** — "There's no current setting for group block reminders, but
there needs to be a setting for that. There should be an on-off toggle, just
like this. And then there should be a setting for interval between reminders."

**Designed** — a fifth row in Email Settings built from the parts already on
that screen: label + ⓘ, a number field with a `Days` suffix, a toggle on the
right, a caption underneath. Four rows already read that way; a fifth that
didn't would look bolted on.

Scott named all three pieces of copy, and they are used as given:

- **Title** — Group Block Reminders
- **Caption** — Interval between each reminder
- **ⓘ** — "When on, the person who created a group block gets a reminder 2 days
  after the block opens, then every 3 days until the block's release date. The
  group block confirmation email sends either way."

The ⓘ wording is Scott's, approved verbatim on 09/09. An earlier version
**echoed the interval you had typed** — set 14 and it said "every 14 days" — so
the sentence always described the schedule actually configured. He replaced it
with static copy that points at the field instead, consistent with his call on
the modal: he would rather the build not pass values into copy.

It still carries the **confirmation-email exception** from PP-42, because the
natural reading of an off switch is that group block email stops entirely.

**Placement** — appended after Hotel User Verification, at the end of the
section. It is the newest setting and the least related to the four guest/hotel
reminders above it, so the end is where it disturbs least.

**Off state** — the interval field stays visible and disabled rather than
disappearing. Pre Arrival sits switched off on this same screen with its field
still on screen; hiding this one would make the row jump and hide the value the
user is about to come back to.

**Validation (PP-43)** — positive integers only. Zero, negatives, decimals,
text and empty are each rejected inline, and both Save buttons disable while the
error stands. See *Proposed · invalid interval*.

## 02 · Registration Settings — the conflict modal

**Asked for** — "when you turn that on and you save settings, the system's
going to check a few things, and if they're all set a certain way, then a modal
should pop up… warning the user: hey, you have compliance reminders and group
block reminders turned on for this event… I think we should say it's recommended
that you turn off group block reminders. And then there's an option to turn off
group block reminders and continue with the save, or save without changing."

**Designed** — an advisory modal on Save, raised only when all three PP-44
conditions hold. The trigger lives in one function, `hasReminderConflict()`, so
the screens can't drift from the ticket.

Three decisions in the modal:

- **It names who is affected.** "Group block creators will get two sets of
  reminders" is the consequence; "you have two settings on" is only the cause.
  The cause is stated underneath, because the user still has to know which two
  things to change.
- **It describes the overlap without naming numbers.** An earlier version put
  the tier count and the configured interval in the sentence, so a Hoco could
  tell whether this meant two emails or nine. Scott replaced it: *"I would
  rather the devs not have to pull in variables to that modal."* The trade is
  real and worth stating — the copy is simpler to build and tells the user less
  about their own situation.
- **Neither button is a cancel, and neither is red.** Both save. They differ
  only in what gets saved, and the recommended one is primary. Advisory means
  advisory.

**Not simulated, on Scott's instruction** — the primary action turning off the
toggle over on Email Settings. "You don't have to simulate that. I just need a
mock of this page." So no state is shared between the two screens; the modal
reports what it did and stops. (PP-44's AC does require the two to stay in sync
in the build.)

## Decisions from the 09/09 review

1. **The X is gone.** PP-44 said dismissing completes the save with both left
   on, which meant an X that silently wrote. Scott agreed it "doesn't make much
   sense" and is adjusting the acceptance criteria. The dialog was already
   `persistent`, so the two buttons are now the only way out.
2. **The modal names no event values.** Tier count and interval removed.
3. **The recipients line is gone** from the Communications card. The condition
   still drives the modal; it is simply no longer visible on the page, so the
   modal can arrive without the user having seen the reason for it.
4. **The ⓘ copy is static**, pointing at the field rather than repeating it.

Both are recorded in **Concepts**, which now marks Modal Dismiss Behavior as
decided (A2) and Next Reminder Preview as declined.

## Still open

1. **The modal headline.** Scott supplied every line of the body but never
   mentioned the title, so *"Group block creators will get two sets of
   reminders"* stands as written. Worth confirming, since he rewrote everything
   around it.
2. **Interval bounds.** PP-43 sets a floor of 1 day and no ceiling. A 365-day
   interval is valid input that silently means "no reminders", and the PRD warns
   about blocks expiring unclaimed when intervals are set too wide. Raised on
   PP-43 and not answered; his "no variables" direction points against the
   release-date-aware warning that would fix it.
3. **Same-day arrival.** The PRD notes that a customer keeping both on may get a
   compliance reminder and a group block reminder on the same day, since nothing
   dedupes them. Raised on PP-44 and not answered — his replacement copy does not
   mention it.
